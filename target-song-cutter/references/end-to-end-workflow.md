# 当前直播切片端到端流程

完整批处理、录播目录续跑或“把所有人的素材都做了”时先读本文件。它规定执行顺序；各模式的精确门禁仍以链接的专项参考为准。

## 0. 入口、存储与稳定性

1. 从 `recording-automation.json` 的 `watch_roots`、当前工作区和用户明确给出的目录发现素材；不要硬编码旧 C 盘路径。
2. 按主播分组，并从 `assets/creator-profiles.json` 读取显示名、角色色、热词、字幕、歌切封面和合集。不得跨主播复用色号、封面底图或投稿文案。
3. 将同场录播的音视频、同名 XML、SC／弹幕导出和已有字幕视为一个 source bundle。先用共享事件校准时间轴。
4. 正在持续写入的录播文件不能作为终稿源。可以处理录播机已经关闭的分段文件或只读稳定快照，但必须把仍在增长的尾段留到稳定后再做完整边界和最终烧录。
5. `ffprobe` 检查时长、流、起点和可解码性。音频始终是剪辑时间轴权威；匹配视频只提供画面。
6. 原录播和 XML 在最终交付审计与云端验证前不得删除、覆盖或拆散。

## 1. 建立整场发现索引

1. 普通叙事先转写整场音频；歌切发现使用中日英多语、关闭 VAD 的分块转写；混合模式对整场只做一次中日英多语转写并从同一结果派生普通选片上下文。
2. 加载常驻热词、VirtuaReal 词表和当前主播 profile 热词。热词只改善识别，不自动决定选材。
3. 同目录存在 Bilibili XML 时运行 `scripts/analyze_engagement.py`。读取多尺度热点、重复弹幕、关键词上下文、原始 SC 和时间轴审计；热点只是回听入口。
4. 有既往评分时运行 `scripts/summarize_clip_feedback.py`，只使用跨至少三个可比样本重复出现的 -1／0／+1 调整。
5. 对共享录播主播刷新 `references/market-benchmarking.md` 所述市场对照。只学习需求和空缺，不复制别人的标题、封面或剪辑。
6. 通读过滤后的转写，先写 `topic-map.csv`，再把语义故事、弹幕热点、SC 引导链、反应、显式选题搜索和历史偏好汇总到 `candidate-report.csv`。

## 2. 选材与库存

1. 每个候选必须能说明 `起因 → 触发／升级 → 结果／反转`，且陌生观众能在最短背景内看懂。
2. 只让 3–5 分叙事候选进入剪辑：4–5 分优先；3 分只补足使原事件成立的最短上下文；1–2 分不剪、不扩写、不做字幕、封面或发布标题。
3. 所有发现过的候选仍写入审计库存。1–2 分和未选中候选只保留短 `candidate_title` 与 `decision_reason`，供投稿后清单使用。
4. 在选材阶段就写 3–5 个有来源证据的片段专属标签；不得等投稿时临时拼热门词。
5. 与已发内容按 source、`topic_key`、核心事件和 payoff 去重；换标题或缩短时长不算新素材。
6. 最终片段若实际保留其他主播的发言，可制作和审核，但默认列入 `已入选但暂缓投稿`，等待用户单独确认；仅提到名字或画面中出现角色不触发此暂停。

叙事门禁见 [editorial-review-gates.md](editorial-review-gates.md)、[editorial-guide.md](editorial-guide.md)、[engagement-signal-fusion.md](engagement-signal-fusion.md) 和 [feedback-calibration.md](feedback-calibration.md)。

## 2A. 混合模式

同场同时找普通切片和歌切时，遵循 [mixed-workflow-template.md](mixed-workflow-template.md)：
只执行一次 Flow 1 和一次 Codex 结构化选片，返回“普通切片”“歌切”两个数组；Flow 3
按每条 content_type 分流标题、封面、VAD、歌词审核和分区。不得把同一录播完整跑两遍，
也不得因其中一类为空再次调用模型。
## 3. 叙事与电台剪辑

1. 为每条候选写非连续 `edit-plan.csv`，只保留钩子、最短背景、升级和完整 payoff。
2. 每个保留区间的开头与结尾都回听源录播前后至少 3 秒。剪点落在完整句意和反应之后，并在最后音节后留约 0.2–0.5 秒自然余量；ASR 分段点不是剪点。
3. 删除无关岔题、礼物感谢、无反应读弹幕、重复解释和只有一次的无意识复读。同一短句连续 4 次以上且形成递进或节奏梗时才完整保留。
4. SC 驱动片段保留相关原文和回答，但剪掉泛化感谢前缀。不得只留回答而丢掉问题。
5. 倒叙采用 `后置爆点 3–15 秒 → 模糊转场 → 最短前因 → 必要时再转场 → 完整结果`。每个非时间顺序跳转都必须渲染总长约 0.5 秒（切点前后各 0.25 秒）、sigma 8–12 的渐进高斯模糊；普通顺序删减不加转场。
6. 先导出实际 review MP4，再对该 MP4 做 clip-local Whisper 和独立 VAD。整场转写不能直接成为成片字幕轴。
7. 核对第一句、片中、片尾和每个拼接点两侧。字幕存在但台词被裁掉、台词存在但字幕缺失、首条字幕来自剪点之前，任一项都重切并重做 ASS。
8. 中文叙事字幕烧录前统一为简体中文，人工修正人名、数字、同音词和说话人。多说话人必须为每条 cue 设置正确 `Name` 与 style；不确定且修复成本过高的片段不交付。
9. 普通横屏叙事默认先交无字幕 review MP4 和同名 ASS；用户已明确要求本批直接烧录时，仍须先通过相同门禁再烧录。
10. 9:16 或电台素材由工作台根据竖屏尺寸或文件名中的电台／radio 自动识别，只交付 1920×1080 左原画／右字幕模板烧录稿和同名 ASS，字号固定 65；封面文案置于右侧信息区。不得交空右栏、普通竖屏重复版或未烧录中间态。

## 4. 歌切

1. 搜索连续歌词区，并额外检查 `唱歌`、`唱一首`、`我们唱歌吧`、`下一首`、歌名提示和 XML 上下文；不得因 ASR 漏唱而漏歌。
2. 为每次演唱建立 attempt 记录。重复开头、伴奏复位、说“重来／再来／错了／等一下”都创建新 attempt；不能把失败前半段字幕接到重开后的演唱。
3. 候选边界必须包含真实前奏、完整唱段、最后一句、延音和伴奏衰减。检查歌核前后至少 60 秒；不得在半句、和弦进行中或仍有音乐时结束。
4. 优先一段连续完整演唱。只有片段时，视频、封面和投稿标题都明确写 `片段`、`一段` 或 `短版`。
5. 以最终无字幕歌切 MP4 为轴，关闭 VAD 重转写；授权歌词、LRC／KRC／YRC 只提供文本和顺序提示，不能替代现场时间轴。
6. 每行歌词听写校正并通过现场锚点门禁。Aegisub／ASS 保持整行位置稳定，按真实字／词起点用约 180–240 ms 的透明度平滑浮现；不缩放、不弹跳、不逐字移动。英文单词、缩写和数字保持完整单位。
7. 中文歌词默认 `AR WeiBeiGBStd BD`；含日语假名的行使用打包的 `Yuji Syuku`。必须提供实际字体文件并通过 `fontsdir`，禁止 PowerPoint 字幕动画和静默字体回退。
8. 当前默认在边界、歌词和 timing gate 全部通过后直接烧录歌切，同时保留无字幕母版和同名 ASS；用户明确要求先审歌词时再暂停。
9. 完整解码烧录成片，并检查开头、三段歌词锚点、最后一句和完整尾奏。

详细门禁见 [media-integrity-and-duet.md](media-integrity-and-duet.md)；歌切底层平滑字幕规范同时遵循 `generic-song-cutter`。

## 5. 同歌合唱／接唱

1. 只把不同主播、经人工确认同一歌名的完整 attempt 配对；同一主播重唱不算合唱候选。
2. 画面两人各占一半。默认使用一条连续伴奏母版贯穿前奏到结尾，按完整歌词段落对齐和切换人声，禁止逐句切换背景音乐。
3. 如果分离人声明显水声、颗粒、相位或合成感，停止使用该 stem，改用 `media-integrity-and-duet.md` 的长段原混音回退；转场必须落在无演唱的伴奏区。
4. 不在半句切换歌手；每段重映射字幕起止，最终再次关闭 VAD 转写并检查所有人声门和尾奏。

## 6. 标题与封面

1. 每条 3–5 分叙事片提供三套不同角度的标题—封面组合：原话冲突、叙事反转、关系／挑战。
2. 本账号标题固定使用前置频道标签：`【中文名English】完整叙事句`。标签只出现一次，`【】` 中只能写主播名，不写“爆点梗概”。
3. 去掉标签和情绪前缀后，正文仍必须包含明确主语、具体动作／遭遇和结果／反转／情绪反应。不能只有“爆了”“破防了”或无主语话题短语。
4. 平台标题不得带文件名前缀编号，如 `001`、`002B`；文件名可保留编号用于本地排序。
5. 普通切片必须同时填写 `cover_text_primary` 上区和 `cover_text_secondary` 下区；每区 3–22 个有效字，并允许在区内手动换一行。标题讲完整小故事，封面上区放具体原话、问题或异常处境，下区补动作、反差、后果或回应。
6. 标题和封面字段严禁英文单引号。
7. 普通叙事封面严格复刻 AutoClip `style1`：原始抽帧不调色、不分区提亮、不加渐变／暗角／卡片；白色主字在 20% 高度，黄色副字在 75% 高度，毛肯石金黑与 12 次黑色描边。
8. 只有最终成片确实保留联动对象可听见的对话时，才在抽帧与文字之间贴审核过的角色表情；仅在房名、画面或提及中出现时不贴。
9. 歌切封面只用 profile 固定底图，78% 高度一行居中黄字：`【枝堇歌／柚雨歌／松绿歌／羽啾歌／昼夜歌】完整歌名`，不得加第二行，不得遮脸。
10. 封面在 1920×1080 和 320×180 两种尺寸检查。标准叙事封面可随成片生成；用户指定“视频直接烧录、封面需审核”时，只暂缓封面批准，不阻塞视频烧录。

## 7. 烧录与交付审计

1. 每条视频、同名 ASS 和 `<video-stem>-cover.jpg` 放在一个扁平交付目录；`titles-and-covers.csv` 与其同级。
2. 烧录只从无字幕母版进行一次。字幕或边界修改后重建，不在旧烧录版上叠字。
3. 运行媒体字幕审计和适用的歌切 timing gate；完整 FFmpeg 解码成片，而不是只探测首帧。
4. 人工抽查开头、片中、结尾、每个剪点和封面小图。任何半句话、字幕错轴、繁体残留、错色、错人名、错合集文案都阻断交付。

## 8. 投稿

1. 投稿是显式选择。先展示并确认每条视频、去编号标题、封面、合集、分区、版权、来源、简介和标签，再执行 biliup。
2. 普通切片进入中文名 `XX切片`，歌切进入 `XX歌`；`XX` 不含 Kioi、Sumire、Viridis、chu2u 等英文。提交时传入已验证的 `season_id`，成功后仍必须按 aid 加入目标 section 并回读确认。
3. 每条作为独立稿件。候选总数不设固定上限；投稿器逐条写成功回执、回读合集并在条目间自动避让，失败后可从回执继续。
4. 只在 BV／aid 恢复、标题精确匹配且合集回读含该 aid 后标记成功。失败即停止，不盲目重投。
5. 账号凭据只保存在 `%LOCALAPPDATA%` 私有文件中，不进入 OneDrive、skill、交付目录、日志或聊天。
6. 完成高分稿件投稿后，必须按日期和主播列出同批 `未入选／未制作`，并单列 `已入选但暂缓投稿`；同时报告候选实例数与唯一标题数。

## 9. OneDrive 归档与可再生成文件

1. 只有最终导出、字幕、封面和交付审计都通过后，才按已验证 source manifest 归档原录播与匹配 XML。
2. 移入 OneDrive 不等于已经上云。必须验证云端资源仍有效、路径和大小匹配，并确认目标为 online-only 后，才可释放本地原文件。
3. 不通过删除待上传副本来腾空间；上传未完成时保留源并报告排队状态。
4. `.venv*`、`__pycache__`、临时 `chunk.wav`、可重跑的 ASR 工作块和中间渲染缓存不属于必须恢复的素材。缺失时可重建，不为它们下载大体积云端副本。
5. 原录播、匹配 XML、人工审过的 edit plan／ASS／歌词 timing、最终 MP4、封面、标题表和投稿审计不是缓存，必须保留或验证云端副本后再清理。

## 10. 完成条件

一次完整批处理只有在以下条件同时满足后才算完成：

- 选材库存完整，只有 3–5 分候选进入成片；
- 叙事或歌切边界、字幕、说话人、字体、色号和完整结尾均通过最终媒体门禁；
- 封面与标题符合当前频道格式；
- 明确要求投稿时，每条已进入正确合集并完成回读；
- 已输出未制作／暂缓投稿清单；
- 明确要求释放空间时，OneDrive 已验证而不是只显示“正在同步”。
