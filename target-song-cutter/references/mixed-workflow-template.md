# 普通切片 + 歌切混合流程模板

当一场直播可能同时包含闲聊爆点和演唱时，在工作台选择“混合切片（普通+歌切）”。
它不是连续运行两套流程，而是共享整场分析和一次 Codex 选片，随后按每条片段的类型分流。
这样不会为同一场录播重复转写或重复消耗模型调用。

## 业务 JSON

混合模式唯一的选片文件是一个对象，包含两个数组。数组内每条仍然只有
“标题”“副标题”“时间戳”三个字段：

~~~json
{
  "普通切片": [
    {
      "标题": "枝堇认真立下保证后被自己下一句话当场拆穿",
      "副标题": "认真保证｜当场拆穿",
      "时间戳": [
        {"开始": "00:12:34.500", "结束": "00:13:20.000"}
      ]
    }
  ],
  "歌切": [
    {
      "标题": "枝堇现场演唱《夏天的风》",
      "副标题": "夏天的风",
      "时间戳": [
        {"开始": "00:24:10.000", "结束": "00:28:35.000"}
      ]
    }
  ]
}
~~~

两个数组都允许为空，条数由本场合格内容自然决定，不预设每类或总计上限。两个数组同时为空表示本场没有合格内容，
任务正常结束为 no_candidates。程序内部才添加 content_type；不要要求模型为每条再输出类型字段。

## 流程 0–2：只做一次

1. 流程 0 验证 FLV／MP4，合并同场断连和 XML 时间轴。
2. 流程 1 对录播自身音轨执行一次中日英多语转写，并从同一份 CSV 过滤礼物感谢。
   XML 的弹幕流速、重复弹幕、关键词和 SC 也只分析一次。
3. 流程 2 用一个 Prompt 和一个结构化 schema，同时返回普通切片和歌切两组。
   不因一类为空再次调用模型，不因本地门禁失败自动消耗第二次调用。

普通切片仍按独立事件的起因、升级和结果筛选；歌切按一次连续演唱 attempt 筛选。
弹幕、SC、“唱歌／下一首”等词和音乐迹象都只能帮助定位，不能独立证明歌名、歌词或边界。

## 流程 3：一次导出，按片段分流

共享同一份 edit plan 和导出任务；titles-and-covers.csv 为每条写入
content_type=narrative 或 content_type=song。

普通切片分支：

- 只删除本条范围中的礼物感谢；
- 对最终导出的 MP4 做 clip-local 中文 ASR 和独立 VAD；
- 生成普通叙事 ASS，叙事标题门禁和普通封面；
- 未解决的 subtitle-vad-qa.csv 行阻断无人值守烧录。

歌切分支：

- 不使用 VAD 裁歌词，不把礼物过滤机械套进演唱范围；
- 对最终导出的 MP4 自动识别语言并保留无 VAD 时间轴；
- 只为歌切行创建 lyric-corrections.csv；
- 歌名封面使用 profile 固定底图和一行“【XX歌】完整歌名”；
- 原始 ASR 只是校对底稿，不能直接成为正式歌词。

## 歌切边界与歌词模板

默认歌切流程把三个问题分开处理：

1. 发现歌段：从报歌名、连续歌词、伴奏变化、弹幕／SC 上下文和重启提示找到候选。
2. 确定歌词文本：人工对照实际演唱和获准使用的歌词来源，逐行填写 corrected_text
   并设置 reviewed=yes。
3. 对齐现场时间：用最终无字幕成片的 no-VAD ASR 作为现场轴，运行
   retime_reviewed_lyrics_from_asr.py；可靠锚点不足时填写人工锚点，不降低门禁。

边界从必要前奏或正式开唱开始，包含最后一句、延音和伴奏释放，并在首次歌后说话前结束。
重复开头、伴奏复位或“重来／再来／错了／等一下”创建新 attempt。优先连续完整演唱；
只有短版时，标题、封面和投稿字段都明确写“片段”“一段”或“短版”。

正式歌词 ASS 由 make_word_fade_ass.py 在流程 4 生成：有可靠字词轴时按真实起点平滑浮现，
没有时使用整行平滑淡入或停下人工对齐。不得把一行时长平均分给字符，也不得烧录未校正 ASR。

## 电台素材

源文件名含“电台／radio”，或 ffprobe 显示画面为竖屏时，流程 3 自动走电台模板：

- 先生成 1920×1080 左侧完整原画、右侧信息区的无字幕母版；
- 普通叙事 ASS 转为右栏居中、字号 65 的角色色样式；
- 审核目录只放烧录可视稿和同名可编辑 ASS，不暴露普通竖屏重复版；
- 封面文案移动到右侧信息区，避免遮住左侧主播；
- 流程 4 从无字幕电台母版和审核后的 ASS 重新烧录一次，不能在审核稿上二次叠字。

## 流程 4–5：同批交付，逐条审计和路由

流程 4 为普通片段复制已审叙事 ASS，为歌切从已审歌词生成正式 ASS。媒体字幕审计对普通
片段额外使用 speech/VAD；现场歌词 timing gate 只检查歌切。最终 MP4、ASS、封面和
titles-and-covers.csv 仍在一个扁平文件夹。

流程 5 按每条 content_type 路由：

- song：音乐分区 tid=130，进入主播的中文名“XX歌”合集；
- 其他：按内容选择分区，不确定时动画综合 tid=27，进入“XX切片”合集。

两类稿件都合并主播 profile 的固定简介和固定 Tag，再加入本条 3–5 个有证据的专属 Tag。
投稿仍需本次明确授权、内容绑定预览和合集回读。

## 为什么默认不装自动判歌模型

开源方案适合做候选或可选增强，但不能取代上述三段式审核：

- [inaSpeechSegmenter](https://github.com/ina-foss/inaSpeechSegmenter) 可分 speech／music／noise，
  但带背景音乐的人声仍可能归为 speech，只适合高召回候选。
- [Demucs](https://github.com/facebookresearch/demucs) 的 --two-stems=vocals 可提取宽泛人声，
  但资源开销大，且不能证明前景主播身份；只在难听清的人工修复场景按需使用。
- [WhisperX](https://github.com/m-bain/whisperX) 的 forced alignment 可挑战失败的词级时间，
  但歌词文本必须先校正，结果仍需听审。
- [All-In-One Music Structure Analyzer](https://github.com/mir-aidj/all-in-one) 可给出
  intro／verse／chorus／bridge／outro 等结构候选，但依赖较重，不能成为默认边界权威。

因此默认模板不恢复“权威音频”“自动判歌”或目标音色识别步骤。模型和检测器只发现候选；
歌词、attempt 和现场边界必须由内容证据与审核门禁确认。
